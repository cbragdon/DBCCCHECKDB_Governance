# File Reference

| File | Purpose |
|---|---|
| `Run_TieredIntegrityCheck.sql` | Main dynamic procedure. Buckets databases by size and runs the appropriate CHECKDB strategy per tier. Self-adapts to AG role, Managed Instance vs. box product, and `@MaxDop` build support. |
| `Rotate_VLDB_ObjectLevelChecks.sql` | Companion procedure providing full logical coverage for VLDB (>= 2 TB) databases via a rotating `CHECKTABLE`/`CHECKALLOC`/`CHECKCATALOG` schedule, since a full logical `CHECKDB` isn't practical nightly at that scale. |
| `Run_LargeTier_WeeklyFullCheck.sql` | Companion procedure providing full logical `CHECKDB` (no `PHYSICAL_ONLY`) for Large-tier (500 GB - 2 TB) databases on a weekly cadence, since the nightly Large-tier check is `PHYSICAL_ONLY` only. |
| `Precheck_RequiredSpaceForSetup.sql` | One-time (or periodic) capacity-planning report to run **before** initial job setup — estimates the disk/tempdb headroom each database's CHECKDB run will need, compares it against currently available space (per-volume on box product, instance-wide on Managed Instance), and flags where to add space ahead of time. Result set 2 starts with `InstanceName` (from `SERVERPROPERTY('ServerName')`) so output is identifiable when consolidating captures from multiple lab/production systems. Both result sets' `ShortfallGB` is only flagged as actionable once it clears a materiality threshold (`@MinMaterialShortfallGB`/`@MinMaterialShortfallPct`, default 2 GB **and** 10% of the required/recommended size) — smaller deltas are reported as `IsShortfallMaterial = 0` / "OK (within estimate margin)" rather than a false alarm, since they're more likely estimate/snapshot noise than a real risk. `ServiceTier` reports `GeneralPurpose`/`BusinessCritical` (via `sys.server_resource_stats.sku`) on Managed Instance, `VM` on box product, or `Unknown` if the tier couldn't be determined — used to give tier-specific remedy guidance when sizing falls short (e.g. GP → scale storage/vCores or check Next-gen GP eligibility; BC → increase vCores). **Note:** "Next-gen General Purpose" cannot be distinguished from classic GP via T-SQL — see the script header for details. On box product, when result set 2's tempdb shortfall is material, the script also validates whether growth can actually happen: it inspects `sys.master_files`/`sys.dm_os_volume_stats` for each tempdb data file and reports `TempdbVolumeMountPoint`, `TempdbVolumeFreeGB`, `TempdbAutogrowthEnabled`, and `TempdbMaxSizeCapGB`. The `Recommendation` then reads either "...NO ISSUE: autogrowth is enabled, no restrictive max size cap, and X GB free..." (autogrowth can cover the shortfall automatically) or "...ISSUE FOUND: ..." naming the specific blocker(s) — autogrowth disabled, a max-size cap below the target, and/or insufficient volume free space — so the report calls out real risk instead of a generic "verify autogrowth" reminder. Not applicable on Managed Instance (tempdb sizing there is fixed by service tier, not manually resizable), so these four columns are `NULL` for MI rows. Result set 1 (per-database volume headroom) gets the same class of growth-safety check on box product: `DataFileAutogrowthEnabled` and `DataFileMaxSizeCapGB` report whether the affected database's own data file(s) have autogrowth disabled or a restrictive max-size cap — if so, and the volume shortfall is material, the `Recommendation` appends a note that adding disk space alone won't fully solve the problem (the file-level setting also needs adjusting). `NULL` for both on Managed Instance (storage there is a shared instance-wide quota, not governed by per-file settings). |
| `Check_DiskAndTempdbHeadroom.sql` | Pre-flight check run before every Large/VLDB-tier operation: tempdb logical free space (both platforms), tempdb/target-DB data-volume free space + IFI status (box product, tagged `(VM)` in messages), and instance-wide provisioned storage headroom via `sys.server_resource_stats` (Managed Instance — protects other databases' data/log growth on MI's shared storage). On Managed Instance, also detects service tier (GP vs. BC) for tier-specific remedy wording in its warnings, same limitation/approach and `VM`/tier naming as `Precheck_RequiredSpaceForSetup.sql` above. Non-blocking; warnings are raised via `RAISERROR` and also persisted to `CommandLog` (`CommandType = 'HEADROOM_CHECK'`). |
| `Monitor_CommandLog_Status.sql` | Reporting query that correctly distinguishes Succeeded/Failed/Running/**Interrupted** (orphaned by a server restart mid-check) rows in Hallengren's `CommandLog` table, plus a second result set of recent headroom-check warnings and a third of the VLDB rotation's object-level checks (`DBCC_CHECKTABLE`/`CHECKALLOC`/`CHECKCATALOG`) from the last 14 days that did not succeed. |
| `Deploy_SQLAgentJobs.sql` | Creates the SQL Agent jobs and schedules that call the procedures above (3 jobs total; the VLDB rotation job runs the list you set in `@VLDBDatabaseList`, and is skipped while that is still the placeholder). **`@MaintenanceDB` has no default and MUST be edited** to your dedicated maintenance database (e.g. `DBAdmin`) before running — the script deliberately `RAISERROR`s and stops if left as the placeholder or set to `master`, since no procedure in this project (or Ola Hallengren's toolkit) should ever be deployed to `master`. |
| `Check_JobScheduleOverlap.sql` | Validates the sequential-execution assumption behind the capacity sizing above. The default schedules created by `Deploy_SQLAgentJobs.sql` all start at 01:00 (nightly job daily, both weekly jobs on their respective day) — if the nightly job is still mid-run (e.g. a Large/VLDB PHYSICAL_ONLY check) when a weekly job kicks off, both compete for disk/tempdb headroom at once. This procedure identifies the governance jobs by job-step command text (robust to renaming), pulls each one's OBSERVED worst-case duration from `msdb.dbo.sysjobhistory` (not a guess — planned duration can't be predicted from schedule metadata alone), and flags any pair of jobs whose scheduled windows can genuinely overlap. Each schedule is laid out on a 7-day timeline, so a run that carries past midnight (including Saturday night into Sunday) is compared with the jobs that start the next morning. Pairs are reported `UNKNOWN (no run history yet)` until both jobs have completed at least one run — re-run after they've executed a few times, ideally during a heavy workload period, for a meaningful result. Works unchanged on both box product and Managed Instance. |
| `Tests_CoreLogic.sql` | Framework-free regression test suite (no tSQLt dependency) covering the pure decision logic most likely to break silently during a future edit: the Small/Medium/Large/VLDB size-tier boundaries, the `IsShortfallMaterial` threshold math, and the job-schedule-overlap day-mask/interval math. Each test reproduces the exact expression from the real script against known inputs and asserts the documented outcome; does not touch any system DMVs or require other procedures to be deployed. Prints a PASS/FAIL row per test and `RAISERROR`s (severity 16) if any failed. Run this after making ANY change to a threshold, boundary, or the overlap math. Because it tests copies, it cannot notice a change to the procedures themselves; `tests/checks/` covers that. |
| `tests/checks/01_Tiering_Routing.sql` | Self-checking test of the installed `Run_TieredIntegrityCheck` and `Run_LargeTier_WeeklyFullCheck` against throwaway `DBCCGovTest_*` databases: tier per database (including one exactly on a boundary), `PHYSICAL_ONLY` and `MAXDOP`, simulated AG primary/secondary roles, and names with `&`, `<`, `>`, `'` and `,`. Uses a test copy of each installed procedure with counted edits (tier sizes in fractions of a GB, scan limited to `DBCCGovTest_*`, a test table in place of `sys.dm_hadr_database_replica_states`). |
| `tests/checks/02_Rotation.sql` | Self-checking test of the installed `Rotate_VLDB_ObjectLevelChecks`, unmodified: coverage over a cycle, only really-checked tables stamped (`@TimeLimitSeconds = 0`), dropped tables removed, awkward database/schema/table names, two databases in one list. |
| `tests/checks/03_Headroom.sql` | Self-checking test of the installed `Check_DiskAndTempdbHeadroom`, unmodified: the tempdb free-space percentage it reports matches an independent measurement at two fill levels; bracket-quoted targets resolve. |
| `tests/checks/04_JobScheduleOverlap.sql` | Self-checking test of the installed `Check_JobScheduleOverlap` with `msdb.dbo.` pointed at test tables (nothing written to msdb): 9 scenarios including runs that cross midnight and the Saturday-to-Sunday wrap. |
| `tests/Run-Checks.ps1` | Test runner: for each requested compatibility level (optionally with the legacy cardinality estimator), creates a disposable maintenance database, installs the toolkit with the installer, checks `QUOTED_IDENTIFIER`, runs `Tests_CoreLogic.sql` and every `tests/checks` script, and drops the database. Exit code 0 only if everything passed; `-ResultPath` appends the rows to a CSV. |
| `docs/LOCAL_TEST_RESULTS_20261026.md` | What was tested on 2026-10-26, how, the results, and what was not tested. |
| `Get-MIServiceTierDetail.ps1` | PowerShell companion script (not T-SQL — this is genuinely not answerable from inside SQL) that resolves the one open question flagged throughout this project's MI-tier warnings: whether a General Purpose Managed Instance is on classic GP or has the Next-gen General Purpose upgrade enabled. Queries Azure Resource Graph for `properties.isGeneralPurposeV2` on every `Microsoft.Sql/managedInstances` resource visible to the caller (one or more subscriptions), and reports an `EffectiveTier` of `Next-gen General Purpose (GPv2)`, `General Purpose (classic)`, or `Business Critical` per instance. Read-only (Reader role is sufficient); requires only the `Az.Accounts` module (no `Az.ResourceGraph`/`Az.Sql` dependency) and an existing or interactive `Connect-AzAccount` login. Cross-reference its `InstanceName` column against `SERVERPROPERTY('ServerName')` (or `Precheck_RequiredSpaceForSetup.sql`'s `InstanceName` column) to match rows to a specific MI. |
| `Install-DBCCGovernanceToolkit.ps1` | Multi-target installer: deploys the six governance stored procedures (everything except `Deploy_SQLAgentJobs.sql`, left as a deliberate manual per-instance step — see its own entry below) to one or more SQL Server VMs and/or Managed Instances against a shared or per-server utility database (`-MaintenanceDB`, default `DBAdmin`) in a single run. Auth is auto-detected per target and is never SQL auth: server names ending in `.database.windows.net` deploy via `sqlcmd -G -C` (Azure AD), everything else via `sqlcmd -E -C` (Windows Integrated Auth) — the same pattern this project's scripts are tested with. Accepts targets directly (`-ServerName`) or from a CSV (`-CsvPath`, see `Targets.example.csv`) for larger fleets. Checks the Ola Hallengren `DatabaseIntegrityCheck` prerequisite per target first — **if missing, it AUTO-INSTALLS it** from the vetted, MIT-licensed copies bundled in `vendor/OlaHallengrenMaintenanceSolution/` (no internet access needed on the target SQL Server), logs it clearly (`[AUTO-INSTALLED]`) per target, and records it in the `HallengrenAutoInstalled` result column; pass `-SkipHallengrenAutoInstall` to require the prerequisite already be present instead. One target's failure never stops the rest (`try`/`catch` per target, `-b` batch-abort on `sqlcmd` so partial-script failures are caught). Supports `-WhatIf` for a dry run. Prints a per-target PASS/FAIL table and returns result objects (pipeable to `Export-Csv` for a deployment record). |
| `vendor/OlaHallengrenMaintenanceSolution/` | Bundled, unmodified, MIT-licensed copies of the three Ola Hallengren scripts (`CommandLog.sql`, `CommandExecute.sql`, `DatabaseIntegrityCheck.sql`) that this project's one hard prerequisite depends on — vendored here solely so `Install-DBCCGovernanceToolkit.ps1` can auto-install them on a target missing the prerequisite, without requiring internet access from the SQL Server itself. See that folder's `README.md` for license/attribution/version details and guidance on refreshing them periodically. |
| `Targets.example.csv` | Example CSV input for `Install-DBCCGovernanceToolkit.ps1 -CsvPath` — `ServerName` (required) and `MaintenanceDB` (optional per-row override) columns. |
| `Tiering-Strategy.md` | Explains the size tiers, thresholds, and the reasoning behind each tier's check strategy. |
| `Platform-Compatibility.md` | Details on SQL Server 2016–2025, Azure SQL Managed Instance, AlwaysOn AG, and JSON index (SQL 2025) compatibility. |
| `Deployment-Guide.md` | Step-by-step install/deployment instructions. |
