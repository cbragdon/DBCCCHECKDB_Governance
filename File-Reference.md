# File Reference

| File | Purpose |
|---|---|
| `Run_TieredIntegrityCheck.sql` | Main dynamic procedure. Buckets databases by size and runs the appropriate CHECKDB strategy per tier. Self-adapts to AG role, Managed Instance vs. box product, and `@MaxDop` build support. |
| `Rotate_VLDB_ObjectLevelChecks.sql` | Companion procedure providing full logical coverage for VLDB (>= 2 TB) databases via a rotating `CHECKTABLE`/`CHECKALLOC`/`CHECKCATALOG` schedule, since a full logical `CHECKDB` isn't practical nightly at that scale. |
| `Run_LargeTier_WeeklyFullCheck.sql` | Companion procedure providing full logical `CHECKDB` (no `PHYSICAL_ONLY`) for Large-tier (500 GB - 2 TB) databases on a weekly cadence, since the nightly Large-tier check is `PHYSICAL_ONLY` only. |
| `Precheck_RequiredSpaceForSetup.sql` | One-time (or periodic) capacity-planning report to run **before** initial job setup — estimates the disk/tempdb headroom each database's CHECKDB run will need, compares it against currently available space (per-volume on box product, instance-wide on Managed Instance), and flags where to add space ahead of time. Result set 2 starts with `InstanceName` (from `SERVERPROPERTY('ServerName')`) so output is identifiable when consolidating captures from multiple lab/production systems. Both result sets' `ShortfallGB` is only flagged as actionable once it clears a materiality threshold (`@MinMaterialShortfallGB`/`@MinMaterialShortfallPct`, default 2 GB **and** 10% of the required/recommended size) — smaller deltas are reported as `IsShortfallMaterial = 0` / "OK (within estimate margin)" rather than a false alarm, since they're more likely estimate/snapshot noise than a real risk. `ServiceTier` reports `GeneralPurpose`/`BusinessCritical` (via `sys.server_resource_stats.sku`) on Managed Instance, `VM` on box product, or `Unknown` if the tier couldn't be determined — used to give tier-specific remedy guidance when sizing falls short (e.g. GP → scale storage/vCores or check Next-gen GP eligibility; BC → increase vCores). **Note:** "Next-gen General Purpose" cannot be distinguished from classic GP via T-SQL — see the script header for details. On box product, when result set 2's tempdb shortfall is material, the script also validates whether growth can actually happen: it inspects `sys.master_files`/`sys.dm_os_volume_stats` for each tempdb data file and reports `TempdbVolumeMountPoint`, `TempdbVolumeFreeGB`, `TempdbAutogrowthEnabled`, and `TempdbMaxSizeCapGB`. The `Recommendation` then reads either "...NO ISSUE: autogrowth is enabled, no restrictive max size cap, and X GB free..." (autogrowth can cover the shortfall automatically) or "...ISSUE FOUND: ..." naming the specific blocker(s) — autogrowth disabled, a max-size cap below the target, and/or insufficient volume free space — so the report calls out real risk instead of a generic "verify autogrowth" reminder. Not applicable on Managed Instance (tempdb sizing there is fixed by service tier, not manually resizable), so these four columns are `NULL` for MI rows. Result set 1 (per-database volume headroom) gets the same class of growth-safety check on box product: `DataFileAutogrowthEnabled` and `DataFileMaxSizeCapGB` report whether the affected database's own data file(s) have autogrowth disabled or a restrictive max-size cap — if so, and the volume shortfall is material, the `Recommendation` appends a note that adding disk space alone won't fully solve the problem (the file-level setting also needs adjusting). `NULL` for both on Managed Instance (storage there is a shared instance-wide quota, not governed by per-file settings). |
| `Check_DiskAndTempdbHeadroom.sql` | Pre-flight check run before every Large/VLDB-tier operation: tempdb logical free space (both platforms), tempdb/target-DB data-volume free space + IFI status (box product, tagged `(VM)` in messages), and instance-wide provisioned storage headroom via `sys.server_resource_stats` (Managed Instance — protects other databases' data/log growth on MI's shared storage). On Managed Instance, also detects service tier (GP vs. BC) for tier-specific remedy wording in its warnings, same limitation/approach and `VM`/tier naming as `Precheck_RequiredSpaceForSetup.sql` above. Non-blocking; warnings are raised via `RAISERROR` and also persisted to `CommandLog` (`CommandType = 'HEADROOM_CHECK'`). |
| `Monitor_CommandLog_Status.sql` | Reporting query that correctly distinguishes Succeeded/Failed/Running/**Interrupted** (orphaned by a server restart mid-check) rows in Hallengren's `CommandLog` table, plus a second result set of recent headroom-check warnings. |
| `Deploy_SQLAgentJobs.sql` | Creates the SQL Agent jobs and schedules that call the procedures above (3 jobs total). **`@MaintenanceDB` has no default and MUST be edited** to your dedicated maintenance database (e.g. `DBAdmin`) before running — the script deliberately `RAISERROR`s and stops if left as the placeholder or set to `master`, since no procedure in this project (or Ola Hallengren's toolkit) should ever be deployed to `master`. |
| `Check_JobScheduleOverlap.sql` | Validates the sequential-execution assumption behind the capacity sizing above. The default schedules created by `Deploy_SQLAgentJobs.sql` all start at 01:00 (nightly job daily, both weekly jobs on their respective day) — if the nightly job is still mid-run (e.g. a Large/VLDB PHYSICAL_ONLY check) when a weekly job kicks off, both compete for disk/tempdb headroom at once. This procedure identifies the governance jobs by job-step command text (robust to renaming), pulls each one's OBSERVED worst-case duration from `msdb.dbo.sysjobhistory` (not a guess — planned duration can't be predicted from schedule metadata alone), and flags any pair of jobs whose scheduled windows can genuinely overlap on a shared active day. Pairs are reported `UNKNOWN (no run history yet)` until both jobs have completed at least one run — re-run after they've executed a few times, ideally during a heavy workload period, for a meaningful result. Works unchanged on both box product and Managed Instance. |
| `Tests_CoreLogic.sql` | Framework-free regression test suite (no tSQLt dependency) covering the pure decision logic most likely to break silently during a future edit: the Small/Medium/Large/VLDB size-tier boundaries, the `IsShortfallMaterial` threshold math, and the job-schedule-overlap day-mask/interval math. Each test reproduces the exact expression from the real script against known inputs and asserts the documented outcome; does not touch any system DMVs or require other procedures to be deployed. Prints a PASS/FAIL row per test and `RAISERROR`s (severity 16) if any failed. Run this after making ANY change to a threshold, boundary, or the overlap math. |
| `Tiering-Strategy.md` | Explains the size tiers, thresholds, and the reasoning behind each tier's check strategy. |
| `Platform-Compatibility.md` | Details on SQL Server 2016–2025, Azure SQL Managed Instance, AlwaysOn AG, and JSON index (SQL 2025) compatibility. |
| `Deployment-Guide.md` | Step-by-step install/deployment instructions. |
